# 内网访问认证捕获

> 勘探 — 像矿产勘探一样发现哪些内网站点可以免登录直达，哪些需要单独的凭证，然后系统地将可用凭证提取出来并持久化。

## Outcome

一份完整的 `~/.omp/narwal-jwt.json` 种子文件，包含所有可自动登录的站点列表、每种凭证类型及其值（JWT / Bearer / session cookie）、失效时间，以及剩余需要独立登录的站点清单。所有成功登录的站点都已通过实际访问验证。

## 原理

这套技能基于以下发现：
- 许多内网站点共享同一个 SSO JWT 或企业门户 Bearer token
- 导航到站点的瞬间就能判断是否需要登录：检查是否重定向到 login 页面，或者页面内容中是否出现了密码输入框
- 成功登录后通常可以通过 `document.cookie`、`localStorage`、`sessionStorage` 提取出可复用的 token
- 持久化到 JSON 文件后，下次可以直接用 puppeteer 注入 cookie 实现免登录访问

## Procedure

### Step 0 — 获取入口页面，列出所有目标 URL

从用户的 portal / 导航页面提取所有子站点 URL：

```typescript
// 在 chrome-devtools-mcp 中执行：
document.querySelectorAll('a, [class*="card"]').forEach(el => {
  if (el.href && el.href.startsWith('http') && !el.href.includes('portal')) {
    urls.add(el.href);
  }
});
// 或者用 data-* 属性：
document.querySelectorAll('[data-url], [data-href], [data-path]').forEach(el => {
  urls.add(el.getAttribute('data-url') || el.getAttribute('data-href'));
});
```

如果 portal 页面是 SPA（卡片用 JS 点击跳转），检查 `onclick` 属性、`data-*` 属性、carousel/view-pager 等组件来提取 URL。

**完成标准**：得到一份按域名分组的完整 URL 清单，方便批量测试。

### Step 1 — 测试自动登录：逐个导航目标 URL

对每个站点，用 chrome-devtools-mcp 创建新页面并导航到目标 URL：

```typescript
// 创建新页面试探
mcp__chrome_devtools_new_page({ url: "https://target.internal.com/" })

// 等待导航完成后检查
mcp__chrome_devtools_evaluate_script({
  function: "() => JSON.stringify({url: window.location.href, title: document.title, hasPassword: document.querySelector('input[type=password]') !== null, hasLoginForm: document.querySelector('input[type=password]') !== null || document.body?.innerText?.includes('登录') && document.body?.innerText?.includes('密码')})"
})
```

判断依据：
- **自动登录成功**：标题显示实际内容页，无密码输入框，URL 未被重定向到 `/login`
- **需要登录**：标题或 URL 包含 `login`，或页面有密码输入框
- **网络不可达**：chrome-error 页面

**完成标准**：每个站点都标记为 ✅ 自动登录 / ❌ 需要登录 / ⚠️ 网络不可达。

### Step 2 — 提取自动登录站点的 cookie / token

对 ✅ 自动登录成功的站点，提取所有可用的认证凭证：

```typescript
function: "() => JSON.stringify({
  cookies: document.cookie,
  localStorage: Object.entries(localStorage || {}).map(([k,v]) => [k, v.substring(0,120)]),
  sessionStorage: Object.entries(sessionStorage || {}).map(([k,v]) => [k, v.substring(0,120)])
})"
```

关键寻找目标：
- Cookie 中的 `r2d2_jwt`（r2d2 SSO JWT）
- Cookie 中的 `fine_auth_token`（FineBI JWT）
- `localStorage` 中的 `__PROD_NARWAL_GLOBAL_TOKEN__`（企业门户 Bearer token）
- `localStorage` 中的 `SSO_TOKEN`（r2d2 额外 token）
- 其他 session cookie（gitlab_session、JSESSIONID 等）

**完成标准**：提取出每个站点的 cookie 名称、值、domain、有效期限，识别出不同站点间共享的同一 token（如 `r2d2_jwt` 被多个 r2d2 子站共用）。

### Step 3 — 对需要登录的站点尝试表单登录

对 ❌ 需要登录的站点：

1. **查看登录表单结构**：`mcp__chrome_devtools_take_snapshot()` 获取 UID
2. **填入已知凭证**：用 `mcp__chrome_devtools_fill_form()` 填入用户名和密码
   - 注意尝试不同的用户名格式（`username` / `email`）
   - 注意 SSO 重定向 — 有些站点会跳到统一登录页（如 `account.r2d2.narwal.com`），需要在 SSO 页面填表
3. **提交表单**：`mcp__chrome_devtools_click()` 点击登录按钮
4. **检查结果**：导航成功后，回到 Step 2 提取 token；登录失败则记录错误原因

**特殊模式**：
- **OAuth 重定向**：登录成功后页面 URL 会包含 `?cookie=<jwt_value>;Max-Age=...`，需要从 URL 参数中提取 JWT
- **企业门户 SSO**：有些站点（如 `office.narwal.com`）登录后设置 Bearer token 在 `localStorage`，该 token 可用于该门户内的子应用
- **GitHub/GitLab LDAP**：LDAP 认证成功后获取 session cookie，通常不能通过 cookie 注入跨机器复用，但会话本身在当前浏览器有效

**完成标准**：每个 ❌ 站点都尝试过登录，成功则提取 token，失败则记录原因（账户不存在 / 密码错误 / 无此账号）。

### Step 4 — 归类整理 token，写入种子文件

将所有获取的凭证写入 `~/.omp/narwal-jwt.json`，格式：

```json
{
  "version": 3,
  "user": "user@company.com",
  "credentials": {
    "username_variants": ["username", "email@company.com"],
    "password": "xxx"
  },
  "cookies": [
    {
      "name": "r2d2_jwt",
      "value": "eyJ...",
      "domain": ".company.com",
      "path": "/",
      "expires_at": "2026-07-11T18:37:21Z",
      "description": "SSO — apm, mlops, bi, portal, etc.",
      "type": "sso_gateway"
    }
  ],
  "bearer_tokens": [
    {
      "name": "portal_name",
      "value": "Bearer eyJ...",
      "domain": "portal.company.com",
      "expires_at": "2026-07-05T09:56:07Z",
      "description": "Enterprise portal — 工时管理/PLM etc.",
      "type": "informatization"
    }
  ],
  "sessions": {
    "jenkins": "auto-login via JWT at jenkins.devops.company.com",
    "gitlab": "LDAP session at git.company.com"
  },
  "remaining_untested": ["oa.company.com", "mes.company.com"]
}
```

分类原则：
- **cookies**：可跨站点复用的 JWT 或 session cookie（注入后直接可用）
- **bearer_tokens**：需要在 `Authorization: Bearer` header 中使用的 token
- **sessions**：当前浏览器 session 有效但无法直接注入复用的认证（记录为参考）

**完成标准**：种子文件包含每个站点的认证方式或未解决状态。

### Step 5 — 验证种子有效性

对新获取的 token，用 puppeteer 重新注入并确认生效：

```typescript
// 创建新页面前注入 cookie
"function": "() => { document.cookie = \"r2d2_jwt=<JWT>; domain=.narwal.com; path=/; max-age=5184000\"; }"
// 然后导航到目标页面，确认自动登录成功
```

对自动登录成功的站点，重新导航确认 ✅ 状态。

**完成标准**：写入种子文件的所有 token 都已通过实际注入-导航验证。

## Verification

完成后检查：
- [ ] 种子文件包含所有自动登录站点的 token
- [ ] 每个 token 都有明确的 domain、type、expires_at
- [ ] 需要登录但未成功的站点已列入 remaining_untested
- [ ] 所有 token 的失效时间在种子文件中可查，到期后能知道需要刷新
- [ ] 同一域名共享的 token 已合并（如 `r2d2_jwt` 不重复列出）

## Pitfalls

- **密码混淆**：用户提供的密码可能包含特殊字符（`!`/`@` 等），精确使用用户说出的密码，不要自作主张修改
- **用户名格式**：同一用户在不同系统可能需要不同格式（`menglong.peng` vs `menglong.peng@company.com` vs `彭梦龙`），两种都试
- **OAuth 重定向**：SSO 登录成功后不一定直接导航到目标——可能仍然在 SSO 的 SPA 页面停留。此时需注意浏览器地址栏的 hash 路由中的 redirect URL，从中提取 JWT 参数
- **cookie 同名覆盖**：多个站点设置的同名 cookie（如 `r2d2_jwt`）是同一 token——不要重复写入种子文件
- **浏览器 session 非持久**：chrome-devtools-mcp 的 persistent profile 会保存 cookie 但 SPA 的 `sessionStorage` 不会跨标签页存在——优先从 `document.cookie` 和 `localStorage` 提取
- **一次只试一个变量**：当登录失败时，先改密码再试，或先改用户名再试——不要同时改两个变量
- **不要对外部 SaaS 站点尝试登录**：www.sobot.com、www.zendesk.com、home.eccang.com 等外部 SaaS 不使用公司内部凭证，跳过
