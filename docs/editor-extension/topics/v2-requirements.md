## 一、平台定位

**一句话：帮助公司提效的平台——让数字员工（agent）成为公司日常运转的一环，把人的时间解放到判断与协作上。**

三条硬约束：

1. **不是审批/管控中心**：审批是安全机制，退居后台——权限在配置层管（新 agent 收紧、成熟 agent 放行），运行期只在需要人判断的时刻打扰（对齐"低优先级不打扰"习惯）
2. **不是 Cursor 平替**：IDE 只是研发团队的工具之一，平台本体是三层数字员工结构
3. **基于 omp 为底座**：agent/sessions/skills/记忆/审批/cron/MCP 全部复用 omp，改内核三端受益（CLI/桌面/IDE/Agent 视图），不复刻

## 二、平台结构（三层 + 一网关）

### L0 员工个人 agent（每人一个）

- 默认绑定钉钉连接器，入口即钉钉（人人都有）
- 定位：**个人上下文引擎**（不是聊天机器人）
- 4 个确定性目标（**常驻运行**，非按需响应）：
  1. **钉钉 context**：通过钉钉获取本人 context（会话/文档/工作动态）
  2. **知识库定期刷新**：定期获取并更新个人知识库，理解用户的工作状态与意图
  3. **画像保鲜**：持续更新 mission 与 user.md，带质量准入（不能越改越乱）
  4. **业务进展秒答**：快速回答用户的业务进展

### L1 域 agent（每域一个）

- 定位：**域的大脑**——统辖域内工作，域内人可对话、请教（销售域 agent 知道销售线所有进展）
- 4 个确定性目标的域化版本：域 context / 域知识库 / 域 mission / 域业务进展
- 附加：**域内协作发起**
- 与员工个人 agent 关系：**双模式**
  - 默认扁平：个人 agent 独立提效，不被打扰
  - 域级任务：域 agent 发起协作，拉人和他们的 agent 进来

### L2 研发智能编辑系统（IDE 视图）

- 研发团队编码工作台，统一走**公司级模型网关 narwal-plan**
- 注：narwal-plan provider 已在 feat/zomp-embedded 实现（`packages/ai/src/provider-models/narwal-plan.ts`，OAuth /login）

## 三、Agent 视图（团队工作台）

- **使用者**（三角色）：
  - 员工：**"我的 agent"轻视图**——看自己个人 agent 的状态/知识库/画像/近期任务/对话入口，与钉钉入口互补
  - 域负责人：分域管理（管本域：域 agent + 域内员工明细）
  - CEO：跨域总览 + 跨域事项
- **驱动**：混合——自动化（cron/事件驱动）+ 交互式（发指令对话）
- **CEO 工作台第一屏：分层下钻**
  - 域级战报（每域一张卡：今日推进/产出/卡点；**数据契约：战报 = 域 agent 的 D4 目标产出**——域业务进展汇总）
  - 跨域事项区（需要 CEO 判断/协调的事——交期冲突、产出异常、资源协调，**不是审批队列**）
  - 点进域 → 域内员工 agent 明细（员工动态归域负责人管）
- **核心功能清单**：
  1. **员工"我的 agent"轻视图**（个人 agent 状态 / 知识库 / 画像 / 近期任务 / 对话入口）
  2. 运转看板（域级战报 / 员工明细两级）
  3. 跨域事项区（判断/协调抓手）
  4. 任务与调度（派活/队列/催办/取消/调优先级）
  5. 治理台（skill / 规则 / 知识库 / MCP 授权 / 模型 / agent 生命周期）
  6. 追溯台（会话/工具调用/决策依据/学习沉淀回放——"敢放手"的底气）
  7. 对话（域 agent / 员工 agent 的沟通入口，查详情的手段，不是视图本体）

## 四、IDE 视图

- **定位**：研发团队项目编码（主）+ 查看 agent workspace 文件（辅）
- **项目选择：双来源分开**
  - 研发项目：IDE 入口打开（git repo，可编辑）
  - agent workspace：从 Agent 视图的 agent 详情跳转进入，**只读预览**；编辑 agent 文件（skill.md / mission.md / rules / cron / 记忆）需**显式授权**进入编辑模式
- **Agent assistant：Cursor 形态完整协作**
  - 侧栏对话面板
  - 选中代码 inline 编辑（⌘K）
  - agent 直接改文件 + **diff 审阅**（接受 / 拒绝 / 手动修改后接受）
  - 审批卡内嵌（与 Agent 视图共用同一套权限策略，同一决策两端看到）
- **底座能力**：文件树 / 多文件编辑 / 保存 / Git 集成（status/diff/log/commit）
- 编辑器内核选型未定（见 §7.1）

## 五、跨视图机制

- **客户端形态（D14）**：单壳收敛——OpenSumi 为唯一客户端壳；Agent 视图 = 壳内自定义视图（LayoutService 动态角色注入）；web-app 资产按优先级迁移进壳后退役（钉钉入口不受影响）
- **UI 风格（D15）**：整体沿用 web-app 风格与动效——自定义 OpenSumi 主题匹配 web-app 设计体系；壳内自定义视图直接复用 web-app 组件/样式；OpenSumi 默认外观不作为客户端长相
- **配置系统（D16）**：沿用 omp 配置系统（config.yml / models.yml / agentDir 等），**不建 ~/.sumi 独立偏好存储**；OpenSumi 偏好仅作 IDE 侧读写代理，schema 与存储归属 omp
- **数据一致**：同一套 agent/session/权限数据，内核唯一
- **审批机制**：存在但不在视图层设中心；权限配置层管理；运行期只打扰需要判断的时刻
- **常驻底座**：gateway（钉钉多账号 = 员工 agent 载体）+ cron（确定性目标的定期触发）+ narwal-plan（模型网关）

## 七、未决问题

1. **技术路线（已定 2026-08-25）**：**OpenSumi 为底座**（spike 验证 4/4 点过，见 `spike-opensumi-verdict.md`）；zomp（Zed fork）分支**冻结不删**作为编辑体验升级的后备研究；路线无关资产（`omp acp` / ACP 测试 / sidecar / narwal-plan provider）并入 main
2. 域内协作的具体形态（域 agent 拉起协作的方式、人在哪里响应）
3. 研发团队的双重身份：研发编码会话是否进运转看板、如何归档（IDE 与三层结构的挂接）
4. 员工个人 agent 钉钉 context 摄入的授权与隐私边界（按人授权，涉及合规宜早定）
5. 分域管理 UI 的多账号/权限模型细化
