# Changelog

- **Fixed: stop button on the v3 OpenClaw AI Card was never visible** (`src/channels/dingtalk-card.ts`): The `675cde2f-f526-40cb-b828-f5b2b57b8b77.schema` template gates the schema's top-right red "中止" button (its onTap fires the `dtActionSheet -> dtSendOutData` chain that delivers `actionId: "btn_stop"` to the server) on the `isTrue(hasAction)` visibility condition. Three bugs in our card paramMap kept `hasAction` false throughout the card lifecycle: (1) `createAICardForTarget` initialised `hasAction: false` in the create body, (2) `cardParamMapForStreamStart` (called on the first `text_delta`) explicitly set `hasAction: false`, and (3) `cardParamMapFromData`'s default for `data.hasAction ?? false` made every subsequent block patch re-set the field to false. Net effect: the schema's only actually-clickable stop affordance was hidden for the entire card lifetime. The fallback path (`blockList[N].btns` with `actionType: "call_back"`) renders as the schema's "当前客户端环境不支持按钮组组件" text with no button. Fixed: initial `hasAction: true` on create, `cardParamMapForStreamStart` keeps it true, `cardParamMapFromData` defaults to true. The `failAICard` path is the one place that explicitly sets `hasAction: false` (it makes sense to hide the stop affordance on an errored card). Verified end-to-end on the hr account: card now shows the red "中止" button throughout streaming, click delivers a TOPIC_CARD callback with `actionId: "btn_stop"`, the gateway aborts the bridge, the chrome shows "（已停止）".

- **Fixed: `Gateway.#handleCardAction` only recognised `params.type === "stop"`** (`src/gateway.ts`): The handler ignored the schema's static stop button (which sends `actionIds: ["btn_stop"]` and `params: {action: "true"}`, no `type` field). With the `hasAction: true` fix above the user could now SEE the button, but a click would still be silently dropped by the handler's "unhandled action type" branch. Fixed by treating `event.actionIds.includes("btn_stop")` as an additional stop trigger alongside `event.params.type === "stop"`. Both shapes route to `sessionManager.abort(accountId)` (and now `sessionManager.abortByUser(userId)` for the registry-miss fallback below). The `matchedBy` log line distinguishes the two paths.

- **Added: `SessionManager.abortByUser(userId)` fallback for unknown card actions** (`src/session-manager.ts`): The OpenClaw schema's `btn_stop` button fires the TOPIC_CARD callback even for cards the gateway never registered with the `ActionRegistry` (e.g. the long-task watcher never ran, so the registry has no `toolName`/`sessionId` for that cardInstanceId; or the registry entry has aged out). The previous handler returned silently in this case, leaving the user with no feedback that their click did nothing. `abortByUser` falls back to aborting the default bridge in the single-account case (the common deployment) and tries every account in the multi-account case, returning `true` if any succeeded. This way an out-of-registry btn_stop click still kills the work the user wanted killed, with a log line showing the fallback path was taken.

- **Fixed: cron model/toolset restore failures were silently swallowed** (`src/gateway.ts`): The `finally` block after cron task execution used `catch {}` for both `setDisabledToolsets` and `setModel` restore calls. If the restore failed, the bridge silently stayed in the cron task's state (wrong model, disabled toolsets) with no log entry. Changed both `catch {}` to `catch (restoreErr) { logger.error(...) }` with context (taskName, cronModel, originalModel, error). Added contract test `test/cron-restore-logging.test.ts` using a fake omp that fails on the second `set_model` call (restore), verifying the error is logged.

- **Fixed: `killOrphanRpcProcesses` killed all PPID=1 omp processes** (`src/gateway.ts`): The function matched `parts[2] === "omp"` on the `comm` column (`ps -eo pid,ppid,comm`), which killed ALL orphaned omp processes regardless of mode — including interactive sessions, `--print` runs, and omp processes started by other gateways. Changed to `ps -eo pid,ppid,args` and match on the full command line requiring both `omp` and `--mode rpc`, so only RPC-mode orphans are killed. Exported the function and added contract test `test/kill-orphan-rpc.test.ts` (6 tests: kills `--mode rpc` orphan; does NOT kill interactive omp, `--print` omp, non-omp with `--mode rpc`, or non-PPID=1 processes; multi-process mixed scenario verifies only correct PIDs are killed).

- **Fixed: DingTalk permission check fail-open on empty allowlist** (`src/channels/dingtalk.ts`): `#checkPermission` returned `true` when `dmPolicy`/`groupPolicy` was `"allowlist"` but `allowedUsers`/`allowedGroups` was empty or missing — silently turning allowlist mode into open mode. An operator who set `dmPolicy: "allowlist"` (intending to restrict access) but forgot to populate `allowedUsers` got open access instead of closed. Changed both `return true` to `return false` (fail-closed). Added test seams `__testCheckPermission` and `__testSetConfig` (following the existing `__testHandleCardCallback` pattern). Added contract test `test/dingtalk-permission-failopen.test.ts` (8 tests: empty/missing allowlist denies all for both DM and group; populated allowlist allows/denies correctly; open/closed policies unaffected).

- **Fixed: scheduler `maxConcurrentRuns` was ignored** (`src/scheduler/engine.ts`): The config field was defined in `SchedulerConfig` (default 3) and passed through `EngineOptions.config`, but the `SchedulerEngine` constructor never read `options.config` — no concurrency tracking existed. Interval tasks whose execution took longer than the interval period would pile up with unlimited concurrent executions. Added `#maxConcurrentRuns` field (read from `options.config`), `#runningCount` counter, and a guard at the top of `#handleTrigger` that skips execution when the limit is reached. The counter is incremented before the execution loop and decremented in a `finally` block. Added contract test `test/scheduler-max-concurrent-runs.test.ts` that schedules a 100ms interval task with a 500ms execution time and `maxConcurrentRuns: 1`, then asserts no more than 1 execution was ever in-flight simultaneously.

- **Fixed: cron warm-bridge fallback was dead code** (`src/gateway.ts`): The fallback guard `if (!output && !stderr)` was unreachable — when `executePrompt` threw, the catch block set `stderr` to the error message (truthy), so `!stderr` was always `false` and the `executeScheduledCommand` fallback never ran. Changed guard to `if (!output)` which correctly identifies "warm bridge produced no result". Added contract test `test/cron-warm-bridge-fallback.test.ts` that injects a fake omp binary (RPC mode returns `success: false` for prompt commands, `--print` mode echoes success) and asserts the fallback's output reaches the execution record. Also added `### Robustness & Fault-Tolerance Testing` section to `AGENTS.md` codifying the methodology: exercise real orchestration paths, inject faults and verify recovery, assert observable outcomes (not logs), fail-before/pass-after verify cycle, and treat testability friction as a code smell.

## [Unreleased]

### Fixed

- **Gateway no longer kills agents during long-running tool calls** (`src/agent-bridge.ts`, `src/prompt-queue.ts`, `src/channels/dingtalk.ts`, `src/config.ts`, `src/types.ts`): The 2026-07-10 06:43 hr-agent `pip install mlx-whisper` incident (62s of no session events → 60s `inactivityMs` watchdog killed the agent) is the root failure mode. Three coordinated changes:

  1. **Long-task watcher now resets the inactivity watchdog** (`src/prompt-queue.ts#fire`): every `onLongTask` fire (threshold + each periodic ping) bumps `pending.lastActivityAt = Date.now()`. Before this, the long-task watcher pushed UI updates but did nothing for the watchdog — the prompt was still considered inactive during a long tool call. The OMP session-event stream produces no events while a bash subprocess is running, so the inactivity timer would tick down to zero and kill a perfectly legitimate long-running tool. Now the only way `inactivityMs` can fire is when the OMP child has truly gone silent (no long-task watcher active either).

  2. **Defaults rebalanced for 2x margin** (`src/agent-bridge.ts`, `src/prompt-queue.ts`): `longTaskThresholdMs` 180s → **50s** (well before the 120s inactivity default, so the stop button appears in the user's card before any kill), `progressPingIntervalMs` 300s → **60s** (1 ping/min keeps the watchdog reset for arbitrarily long tool calls), `inactivityMs` default 60s → **120s** (lets the streaming watchdog at 90s catch real OMP hangs without false-positive-killing long bash). The 60s ping / 120s inactivity pairing has 2x margin (no race between ping fire and watchdog tick).

  3. **DingTalk AI card ping text reformatted** (`src/channels/dingtalk.ts#streamCard`): the threshold fire keeps the existing rich text (`⏳ **bash** 已运行 3 分钟。点击下方按钮中止。` + 停止 button). Each subsequent ping overwrites the stop block's text with a compact `⏳ 3m 12s` (no tool name, no button reminder — the button is already in the block). Format C: detailed first, then ticking. Hermes-style periodic notify pattern.

  Both new fields are exposed in `gateway.json` `agent` block: `longTaskThresholdMs` (0 disables) and `progressPingIntervalMs` (must be positive). Verified end-to-end against the 2026-07-10 repro: a fake RPC emitting one `bash` tool call and holding for 10s with `inactivityMs: 1_000`, `longTaskThresholdMs: 100`, `progressPingIntervalMs: 200` survives the full hold (no `Agent RPC inactive for Xms` reject, prompt resolves cleanly when the tool result arrives).

### Fixed


- **AgentBridge sent redundant `set_model` on every IM message** (`src/agent-bridge.ts`): `forwardWithMeta` and `executePrompt` sent `set_model` unconditionally whenever `#configuredModel` or `#pendingModelOverride` was set, regardless of whether `#switchSession` actually switched sessions. In the OMP subprocess, each `set_model` call invokes `AgentSession.setModel()`, which appends a `model_change` entry to the session JSONL, closes openai-responses/codex provider sessions (forcing reconnection on the next LLM call), writes to settings storage, and re-applies thinking level — all redundant when the model hasn't changed. Fixed by making `#switchSession` return `boolean` (whether a real switch occurred) and gating `set_model` on `sessionChanged || #needsModelReapply`. Added `#needsModelReapply` flag set on `disconnected` events (crash/exit) so the model is re-applied after subprocess restart even when the session path is unchanged.

- **AgentBridge `disconnected` event did not clear `#activeSessionPath`** (`src/agent-bridge.ts`): When the OMP subprocess crashed, `#activeSessionPath` retained the stale path. On recovery, `#switchSession` saw `#activeSessionPath === targetPath` and early-returned without sending `switch_session`, so messages were written to the subprocess's default session file instead of the gateway-tracked file. Fixed by clearing `#activeSessionPath` and setting `#needsModelReapply = true` in the `disconnected` handler.

- **`executePrompt` did not re-apply model for sessionless cron tasks after crash** (`src/agent-bridge.ts`): The `set_model` call was inside the `if (sessionPath)` block, so cron tasks without a `sessionPath` never got the model re-applied after a crash recovery — the subprocess ran with its default model instead of the configured one. Fixed by moving `set_model` outside the `sessionPath` block with the same `sessionChanged || #needsModelReapply` gate.

- **`set_model` failures were logged at `warn` level** (`src/agent-bridge.ts`): A failed `set_model` left the agent running with the wrong model, but the error was only `logger.warn` — invisible to operators monitoring for errors. Changed to `logger.error` in all three call sites (forwardWithMeta, executePrompt, executePrompt recovery path).
- **`omp gateway service start` reported spurious "Bootstrap failed: 5: Input/output error" after install** (`src/service-installer.ts`): `launchctl bootstrap` against an already-loaded service returns errno 5 (EIO), not the older "already bootstrapped" string the previous `startService` looked for, so the error-handler threw every time the operator ran `start` immediately after `install` (install does its own bootstrap; the second bootstrap hits EIO) even though the gateway was in fact running. `startService` now asks `getServiceStatus()` first and short-circuits when the service is already up, making it idempotent on both macOS and Linux. The Linux `systemctl --user start` path was already idempotent and is unchanged.

- **`omp gateway service install` lost `~/.local/bin` from PATH on every reinstall** (`src/service-installer.ts`): the launchd plist and systemd unit templates hardcoded a PATH that started at `${HOME}/.bun/bin` and never listed `~/.local/bin`, where user-installed CLIs (`dws`, `agent`, `cursor`, `hermes`, `uv`, ...) live. The supervised gateway's agent runs each `bash` invocation as a non-interactive shell that does NOT source `~/.zshrc`, so any tool that the operator's interactive shell could find in `~/.local/bin` was `command not found` to the agent — symptom was intermittent (worked when an earlier bash call had manually set `PATH`, failed on a fresh one). New exported `gatewayServicePath(env)` helper is the single source of truth for the supervised gateway's PATH; both the launchd plist and the systemd unit pull from it, so the two configs can't drift. The helper also reads from the `env` argument (so tests can hermetically pin HOME) instead of module-level `process.env.HOME`. `~/.local/bin` listed first so user-local binaries win over system ones. New `gatewayServicePath` tests in `test/service-installer-env.test.ts` lock the ordering and lock `~/.local/bin` in both plist and systemd `Environment="PATH="` output.

- **Fixed: oversized DingTalk inbound attachments were silently dropped as `[non-text message]`** (`src/channels/dingtalk-media.ts`, `src/prompt-extractor.ts`, `src/types.ts`, `test/dingtalk-media.test.ts`): When a user sent a file (typically a PPTX deck) larger than `MAX_INBOUND_ATTACHMENT_BYTES` (20 MB), the gateway would (1) download the file in full, (2) drop it because it exceeded the cap, (3) hand an empty `attachments: []` array to the prompt-extractor, (4) fall through to the "non-text message without attachments" branch — the agent saw `"[non-text message]"` and could not tell the user anything was lost. Repro'd live on `hr` at 2026-07-08 17:39 with a 37 MB `庄小平-世界模型-转正述职材料.pptx`. Three coordinated fixes: (a) `MAX_INBOUND_ATTACHMENT_BYTES` raised 20 MB → 100 MB to match `MAX_VIDEO_DOWNLOAD_BYTES` (the old figure was a misread of DingTalk's *upload* limit, not a download limit); (b) new exported `makeInboundAttachment(downloaded, kind, filename)` helper runs the size guard and returns a metadata-only `InboundAttachment` with `status: "too_large"` instead of `null` when over the cap — the bridge gets `{ kind, data: Uint8Array(0), mimeType, filename, size, status }` so it can surface the situation; (c) `prompt-extractor.classifyAttachment` now branches on `att.status === "too_large" | "download_failed"` first and produces `[file: 庄小平-...pptx (application/vnd..., 37.0 MB) — exceeds inbound size limit, bytes not retained; ask the user to re-upload a smaller file or paste the relevant text]` instead of the misleading placeholder. New `status` field on `InboundAttachment` (typed `"ok" | "too_large" | "download_failed"`, defaults to `"ok"` for older callers) is the explicit contract for "bytes not available". `downloadOneAttachment` refactored to always clean up the temp dir in a `finally` block (previously only the too-large path cleaned up; the success case leaked the temp dir). 3 unit tests on `makeInboundAttachment` + 2 e2e tests on the bridge forwarding (asserting the prompt contains the filename, the formatted size, and a non-`[non-text message]` sentinel) lock the new contract.

If `unzip` is unavailable or the buffer isn't a valid PPTX the helper returns `""` and the prompt-extractor falls through to save-to-disk so the agent's own bash tool can dig in. End-to-end bridge test confirms a real PPTX attachment surfaces `[PPTX: okr-q3.pptx]\n[Slide 1]\nQuarterly OKR review ...` in the agent's prompt.

- **Fixed: HTTP 200 with error body silently treated as success across all AI Card calls** (`src/channels/dingtalk-card.ts`, `test/dingtalk-card.test.ts`): The 2026-07-10 long-task repro surfaced the exact bug — DingTalk returns HTTP 200 with body `{"code":"system.busy","message":"system.busy","requestid":"..."}` to signal failure on the card streaming / patch / FINISHED endpoints, but the channel only checked `resp.ok` (HTTP status). 3 `patchAICardBlocks` calls all returned 200+system.busy and were silently dropped, so the user saw the streamed text but none of the blockList updates (no ping, no tool result) even though the log showed 3 `[DingTalk] patchAICardBlocks` events with zero error entries. New exported `parseDingtalkError(body)` helper parses the response body and returns `{code, message, requestid}` when the body contains a non-`ok`/non-`0` `code` field, `null` otherwise (success bodies in the wild are `{}` with no `code` field; the `code === "ok" | "0"` whitelist is defensive against a future schema adding a code field to success bodies). Applied at all 6 sites: (1) `createAICardForTarget` create instance — body-code error returns `null` so the channel falls back to v1 markdown; (2) `createAICardForTarget` deliver — same; (3) `streamAICard` INPUTING switch — logs error so the card isn't stuck in PROCESSING; (4) `streamAICard` streaming — logs warn, next delta will retry; (5) `patchAICardBlocks` — logs warn, absorbed by the per-card catch; (6) `finishAICard` — treats body-code error as transient, routes through the same retry/backoff path as a 5xx, and after `FINISHED_MAX_RETRIES` exhausted throws `FINISHED update failed after 3 retries: status=200 body=...` so the bridge fallback to v1 markdown still fires. The 403-retry path's second fetch also gets the body-code check (a retry that succeeds at HTTP level but returns `code: "system.busy"` in the body is still a failure). 8 new unit tests on `parseDingtalkError` (non-ok code, QpsLimit, ok/0/empty/non-JSON/non-object bodies, missing fields) + 3 new `patchAICardBlocks` integration tests (silent success on 200+empty body, 200+system.busy does NOT throw, 500 still warns) + 2 new `finishAICard` integration tests (200+system.busy retries then succeeds, 200+system.busy persistent throws with the new error message). 42 tests in `dingtalk-card.test.ts` all pass.

### Added

- **Unified cron-session storage under per-agent `sessions/`** (`src/session-paths.ts`, new file, ~250 lines): The single source of truth for where a session file lives. Five exports, one job each: `encodeCwd(cwd)` produces the `by-date` directory segment; `cronSessionPath(agentDir, now?)` returns `<agentDir>/sessions/cron_<ts>.jsonl` (flat, deterministic timestamp); `interactiveSessionPath(agentDir, cwd, now?)` returns `<agentDir>/sessions/<encoded-cwd>/by-date/<YYYY-MM-DD>/<HHMMSS>__<8hex>.jsonl` matching OMP's interactive layout; `findAgentSessionPath(agentDir, startedAt, endedAt)` scans only `<agentDir>/sessions/` with a ±5 s tolerance window (latest-mtime-wins for ties); `enumerateAgentSessions(agentDir)` lists everything under the agent's session tree as `{path, type, size, mtimeMs}[]`. Filename grammars are documented and tested: cron is `^cron_\d+\.jsonl$`, interactive is `^\d{6}(?:-[a-z0-9-]+)?__[0-9a-f]{8}\.jsonl$`. Replaces the implicit three-place path decision (cron lifecycle constructed one path, OMP's default by-date fallback constructed another, the legacy global walker accepted a third) that caused cron runs to leak to `~/.omp/agent/sessions/<encoded-cwd>/by-date/...` instead of the agent's own dir.
- **`cron.recent` host tool action — IM LLM can fetch scheduled-task output on demand** (`src/scheduler/types.ts`, `src/scheduler/storage.ts`, `src/scheduler/json-file-storage.ts`, `src/scheduler/host-tool.ts`, `test/host-tool.test.ts`, 11 new tests): New `recent` action on the existing `cron` host tool returns the most recent execution history across all the agent's tasks (newest first), each row carrying `taskName` / `startedAt` / `endedAt` / `durationMs` / `status` / `exitCode` / `agentSessionPath` and a `outputExcerpt` of the captured report text truncated to 2000 chars by default. Filters: `name` (single task), `limit` (default 5), `sinceMs`, `includeOutput` (default true), `outputMaxChars` (default 2000, pass 0 for full output). Solves the "user DMs '执行建议 / 按上次的来 / follow up 上次报告' and the new IM-session agent has no idea what the previous report said" gap — the LLM calls `cron.recent` on demand, scans the excerpt for `## 建议操作` / `## Next steps` / similar sections, and acts. Underlying `SchedulerStorage.getRecentExecutions({ limit, taskName, sinceMs })` added to the interface and implemented in both backends (SQLite via cross-task JOIN, JSON-file via per-task log walk + in-memory merge). Output truncation uses middle-truncation (preserves head + tail) so the actionable tail of long reports survives the 2000-char cap. Storage mock in `test/scheduler-cron-service.test.ts#makeStorageMock` updated for the new interface method.

- **`scripts/sweeps/empty-cron-dirs.sh`** (new, `scripts/sweeps/empty-cron-dirs.sh`): Housekeeping script that removes empty `cron_<id>/` artifact sidecar directories under an agent's `sessions/` dir. The oclif rewrite of the gateway command dropped this call. Result: a gateway restart would lose the restart-sentinel recovery path. The call is restored in `coding-agent/src/commands/gateway.ts#start.foreground`, wrapped in `try/catch` with a `logger.warn` on failure (matching the original behavior).

- **`SchedulerEngine` auto-disabled test-run one-shots, racing the test-run's `finally` restore** (`src/scheduler/engine.ts`, `src/scheduler/test-run.ts`, `test/scheduler-engine.test.ts`): `engine.ts` set `tasks.status = "disabled"` unconditionally after a one-shot's `setTimeout` fired. The test-run core (`test-run.ts`) snapshots the original schedule, rewrites the task to `cron="+<n>s" scheduleType="once"` to fire through the real scheduler, then restores the snapshot in a `finally` block. The engine's `await this.#handleTrigger(task.id)` and the test-run's `await Bun.sleep(pollIntervalMs)` could complete in either order: when the engine won, the test-run's `restoreSnapshot` would set `status="active"`, but the engine's continuation would then write `status="disabled"` and the DB ended up with `cron="+<n>s", status="disabled"`. The test-run reported `scheduleRestored: true` (the local `restored` flag was set inside `restoreSnapshot`) but the on-disk state was still disabled, and a subsequent `omp gateway cron list` showed the wrong state. Net effect: any test-run (CLI `cron test-run` or LLM `cron.test-run` action) left the task in a half-disabled, half-rewritten state — verified on `daily-2000-calendar-push` after `inMs=90000`: DB ended as `cron=+90s, schedule_type=once, status=disabled, next_run_at=null` instead of the original `cron=0 20 * * *, schedule_type=cron, status=active`. Fix: `isTestRunSchedule(cron)` helper (`/^\+\d+s$/`) detects the test-run marker shape. The `setTimeout` callback now SKIPS the post-execution `status="disabled"` write when the schedule matches — the test-run's `finally` becomes the final word on the task's state. Real one-shot tasks (user reminders, ISO-timestamped jobs, ad-hoc cron expressions) are unaffected and continue to auto-disable. Marker contract is one-way: only `test-run.ts:runTestRun` writes the `+${delaySec}s` shape; if you change that line, change the regex in lockstep. The existing "clears one-shot nextRunAt after execution" test was retargeted from `cron: "+30ms"` to `cron: <ISO timestamp in 30ms>` to keep pinning the real one-shot auto-disable behaviour, and a new regression test (`does NOT auto-disable one-shots with a test-run schedule (+<n>s)`) pins the marker behaviour. 80/80 scheduler tests pass.

### Removed

- **`initTheme()` call from the gateway oclif command**: The gateway command is non-interactive; it never renders TUI components. `initTheme()` was a leftover from the original TUI-mode command shape, loading theme files and (when enabled) starting a filesystem watcher for the theme directory. The call did no useful work in this command and added startup time.

### Changed

- **`installService()` no longer takes a `cliPath` argument** (`src/service-installer.ts`): The plist / unit is now built from the current `process.execPath` and (in dev mode) `process.argv[1]`. Dev mode is detected the same way as the daemonize path in `coding-agent/src/commands/gateway.ts` (argv[1] ends in `.ts` or `.js`). The old signature forced callers to pre-resolve a path that only made sense in dev mode (`<pi-gateway>/src/cli.ts`) and silently produced a broken plist when invoked from the compiled `omp` binary. Both modes now route to the same oclif gateway command.

### Removed

- **`getRuntimePath()`** (`src/service-installer.ts`): The function did two unrelated things — runtime selection (`process.execPath` vs `Bun.which("bun")` based on `PI_COMPILED`) and conflated entry-file passing through its return value. With the new dev/prod detection on argv[1], the runtime is just `process.execPath` (which is `bun` in dev, the `omp` binary in prod) and the entry file is a separate `process.argv[1]` element.

### Breaking Changes

- **`pi-gateway` binary is removed**. The `bin` entry is gone from `packages/pi-gateway/package.json`. There is no longer a standalone `pi-gateway` CLI on disk or via `npx`. All gateway operations are reached through the unified `omp` binary:
  - `pi-gateway start` → `omp gateway start`
  - `pi-gateway stop` → `omp gateway stop`
  - `pi-gateway status` → `omp gateway status`
  - `pi-gateway config` → `omp gateway config`
  - `pi-gateway reload` → `omp gateway reload`
  - `pi-gateway doctor` → `omp gateway doctor`
  - `pi-gateway setup` / `pi-gateway install` → `omp gateway setup`
  - `pi-gateway cron ...` → `omp gateway cron ...`
  - `pi-gateway service ...` → `omp gateway service ...`
  - `pi-gateway test-longtask ...` → `omp gateway test-longtask ...`
  The `omp` invocation is the single entry point and works in both dev (`bun packages/coding-agent/src/cli.ts gateway ...`) and prod (compiled `omp` binary) modes.
- **`packages/pi-gateway/src/cli.ts` is deleted**. The 776-line legacy CLI is gone. All command dispatch is handled inline in `coding-agent/src/commands/gateway.ts`. Anyone importing from the deleted file (none in this repo) will need to migrate to the oclif gateway command.
- **`omp schedule ...` is removed**. The hidden compatibility shim that mapped `omp schedule` actions to `pi-gateway cron` is deleted. Use `omp gateway cron ...` for all schedule operations.

### Fixed

- **`buildCronContextPrefixFromStorage` Tier 3 silently skipped on gateway restart between a failed run and the next scheduled trigger** (`src/scheduler/execution-log.ts`, `src/scheduler/json-file-storage.ts`, `src/scheduler/cron-service.ts`, `src/scheduler/cli-commands.ts`, `test/scheduler-execution-log.test.ts`, `test/scheduler-storage-persistence.test.ts`): The agent session path was being set via `storage.updateExecution(...)` on the in-memory Map only — `appendExecutionLog(...)` did NOT include the field, so the on-disk JSONL log had no record of it. After a gateway restart (or any fresh `JsonFileStorage` instance) `getExecutions()` rebuilt the row from the JSONL log entry, which had no `agentSessionPath`, so the new run's Tier 3 (`if (... && lastExec.agentSessionPath)` in `cron-service.ts:284`) silently skipped. The visible symptom was: a real cron failure happened, the gateway restarted, and the next run had no idea the previous run had failed or which tool calls to look at. The fix is a 4-place round-trip: `ExecutionLogEntry.agentSessionPath?` added to the log schema, all three `appendExecutionLog` call sites (`cron-service.ts:687`, `cli-commands.ts:543`, plus the catch path) include the field via spread, and `JsonFileStorage.getExecutions` reads `entry.agentSessionPath` back from the log. Legacy entries written before the fix surface as `undefined` (no synthetic value — that would have masked the original bug from operators debugging an upgrade). Two regression tests: `test/scheduler-execution-log.test.ts` "preserves agentSessionPath on appendExecutionLog → readExecutionLog" + "omits agentSessionPath for legacy entries"; `test/scheduler-storage-persistence.test.ts` round-trips a full storage #1 → storage #2 (simulated restart) and verifies the path survives.

### Added

- **`forceFail` debug-only override on `ScheduledTask`** (`src/scheduler/types.ts`, `src/scheduler/cron-service.ts`, `test/scheduler-cron-force-fail.test.ts`, 7 tests): Tasks can now set `forceFail: true` in `jobs.json` to force the next run to be recorded as `exitCode: 1, status: "failure"` regardless of whether the warm bridge or fallback succeeds. The warm bridge still runs normally (so the real agent session is created and tool calls are recorded), then a single override block sets `exitCode = 1` and appends a `[forceFail]` marker to the output. The field exists to enable end-to-end verification of Tier 3 (the previous-run tool-calls recap) — natural cron failures are hard to produce in the test harness because the warm bridge's `executePrompt` does not respect `timeoutMs` as a hard cap (the LLM call's intermediate messages reset the inactivity timer) and the cold-subprocess fallback covers most failure cases with a successful `omp --print` run. The override is a debug-only knob: it is documented as never-to-be-set in production task definitions, it only fires on the post-fallback success path (`exitCode === 0` → override to 1) so a real failure is never stomp on, and the `[forceFail]` marker in the recorded output makes the override visible in production logs. Tests cover: warm-bridge success → override fires; agent session path preserved; `[forceFail]` marker appended; failure-flavored summary card delivered; warm-bridge AND fallback both failed → no double-override; `forceFail: false` or absent → no behavior change.

- **`parseAgentSessionForToolCalls` silently returned no tool calls on every modern OMP session** (`src/scheduler/diagnostics.ts`, `test/scheduler-parse-tool-calls.test.ts`, 3 new tests): the parser only handled the legacy `tool_execution_start` event (`{ toolCallId, toolName, args }`) and missed the current OMP client format, which emits the tool_use inline within the assistant message as `content[].type: "toolCall"` with `{ id, name, arguments }`. The first-pass args-collection now also walks assistant content blocks and populates the same `argsByToolCallId` map keyed by the inline `id`, so the second-pass toolResult correlation works for both formats. Without this fix Tier 3 of the cron context prefix would have returned zero tool calls on every cron run that went through a current OMP client — exactly the silent-skip the persistence fix above was supposed to defeat. The 3 new tests cover: pure inline format, mixed legacy+inline in the same session, and `[ERROR]` tag propagation from an inline-format failure.
