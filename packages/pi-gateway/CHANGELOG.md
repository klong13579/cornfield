# Changelog

## [Unreleased]

- **DingTalk AI Card v2 (PROCESSING → INPUTING → FINISHED state machine)**: `DingTalkChannel.streamCard` runs the agent response through a platform-native AI Card, replacing the "thinking..." placeholder with an animated card. Lifecycle: card is created in PROCESSING state on inbound message, transitions to INPUTING on the first `text_delta` (the bridge's new streaming callback), streams the assistant text into the card with a 1s throttle (collapses bursts of `text_delta` events into one `streamAICard` call per window), and finishes with FINISHED + the full v1-formatted chrome (quoteContent / tool summary / status line) on `agent_end`. If the channel doesn't support cards (Feishu / WeChat / custom) or card creation fails (DingTalk API 5xx, auth failure, group target resolution failure), the gateway transparently falls back to the v1 markdown path (placeholder + `formatReply`) so users always get an answer. 6 new types / 1 new method on the `Channel` interface, 2 new bridge methods (`forwardWithMeta` streaming callbacks, `enqueueWithMeta` handlers pass-through), 1 new `setConfig` test seam on `DingTalkChannel`. 5 new tests: 3 in `test/agent-bridge-streaming.test.ts` pin the bridge's `onTextDelta` / `onThinkingDelta` / `onAssistantMessageEnd` / `onAgentEnd` firing order with cumulative-text tracking, 2 in `test/dingtalk-card-e2e.test.ts` spin up a fake `api.dingtalk.com` server to assert the full create → deliver → stream → finish lifecycle (with a separate "card creation fails → null" case for the v1 fallback path).

- **AgentBridge streaming callbacks**: `AgentBridge.forwardWithMeta(msg, session, handlers?)` now accepts an optional `ForwardStreamHandlers` block. The bridge fires `onTextDelta(delta, cumulative)` for every `text_delta` event from the agent loop, `onThinkingDelta(delta)` for `thinking_delta`, `onAssistantMessageEnd()` on the assistant `message_end`, and `onAgentEnd()` on `agent_end`. The bridge's inline `AgentEvent` interface gained an `assistantMessageEvent` field so the `message_update` payload reaches consumers; the bridge's local type is deliberately narrower than the full `@oh-my-pi/pi-agent` `AssistantMessageEvent` (the wire carries the full shape but the bridge's local view is just enough for the streaming extraction path). Handlers fire synchronously on the bridge's event-loop turn — a handler that throws is logged and the run continues. The full `AgentResponseMeta` is still returned at run end for callers that also need the final reply chrome. Backward compatible: callers that don't pass `handlers` see no behavioural change. Used by the AI Card path; the cron scheduler and other fire-and-wait callers don't pass handlers.

- **`Channel.streamCard` interface**: New optional method on the `Channel` interface lets each platform opt into the v2 AI Card streaming path. The method takes the inbound message, session, per-account `ReplyFormatterContext`, and a `submit` function bound to `SessionManager.enqueueWithMeta`; the channel decides whether to use a card (DingTalk does, others return `null` and the gateway falls back to v1 markdown). The `submit` argument is the seam that lets the channel subscribe to streaming events without importing the bridge directly — it just passes `handlers` through. `ForwardStreamHandlers` is re-exported from `types.ts` so the `Channel` interface can type the `handlers` parameter without a circular import on `agent-bridge.ts`.

- **`SessionManager.enqueueWithMeta` handlers pass-through**: `enqueueWithMeta(msg, session, handlers?)` now threads `ForwardStreamHandlers` through to `AgentBridge.forwardWithMeta`. The queueing / serialization contract is unchanged; only the bridge call gains the new optional parameter. Backward compatible.

- **Cron warm-bridge session isolation**: `AgentBridge.executePrompt` now accepts an optional `sessionPath`. The gateway uses this to give each cron task its own JSONL session file at `<agentDir>/sessions/cron_<taskId>.jsonl`, so cron state no longer pollutes the active IM session. The whole switch/prompt/restore sequence runs under the bridge's `#runExclusive` lock, so it is atomic with respect to other IM traffic sharing the bridge. After the prompt completes, the bridge restores the prior session (when one was active) so the next IM message lands back in its own session. New 4-case `AgentBridge.executePrompt (cron path)` test block pins the empty-prompt throw, the pre-prompt switch, the post-prompt restore after a prior IM session, and the cold-bridge no-restore case using a recording fake RPC.
- **Cron warm-bridge skills/preScript warning**: When a cron task that targets the warm-bridge path has `skills` or `preScript` set, the gateway now logs a `warn` explaining that these fields cannot be honoured on the warm path (the long-running bridge has no shell to run preScripts and cannot load per-task skills beyond what the agentDir already provides). Operators see the limitation in logs instead of discovering that task.skills silently does nothing. Fall back to `omp -p` (remove `--account`) to honour them. New test for the cwd path (`test/scheduler-executor-cwd.test.ts`) confirms that `executeScheduledCommand` honours the `cwd` option for shell tasks, so the gateway's fallback now runs in the correct account's `agentDir` and finds the right `.omp/config.yml`.
- **Cron inactivity watchdog**: `AgentBridge.executePrompt` now accepts an optional `inactivityMs` budget. While the prompt is in flight, a per-prompt `setInterval` (500ms poll) checks the prompt's `lastActivityAt` (bumped on every session event in the reader) and aborts the prompt if no event arrives within the budget. The watchdog reuses private RPC methods rather than `bridge.abort()` to avoid a re-entrant deadlock against `#runExclusive`. Default 5 min, capped at 30 min, never exceeding the wall-clock `timeoutMs`. Gateway uses this so a stuck RPC or hung tool can't pin a task for the full wall-clock timeout. 3 new bridge tests cover: inactive prompt aborts within ~1s, slow-but-active prompt survives, and `inactivityMs` opt-in is respected (no watchdog when not set).
- **Cron delivery retry + failure log**: The gateway's cron result delivery is now awaited (was fire-and-forget) with one 5s retry for transient channel failures. Persistent failures write a JSONL line to `~/.omp/gateway-data/scheduler/logs/delivery-failures.jsonl` with taskId / taskName / channel / userId / reason / attempts / exitCode, so operators can see which task results never made it to the channel even after a gateway restart. The task's own exit code is preserved (delivery failure ≠ task failure). 3 new `appendDeliveryFailureLog` tests cover single-write, multi-write, and nested-log-root creation.
- **Cron soft recursion guard (CRON-CONTEXT prefix)**: The gateway prepends a `[CRON-CONTEXT] You are running as a scheduled task ...` block to every agent cron prompt (both warm-bridge and fallback paths), asking the agent to avoid spawning follow-on cron jobs or sending unprompted messages to other channels. This is the OMP analog of Hermes's `disabled_toolsets=["cronjob","messaging","clarify"]` — OMP has no equivalent toolset filter at the CLI level, and forcing `--tools` restrictions would break legitimate bash-heavy cron work. New `promptPrefix` option on `executeScheduledCommand` carries the prefix through the fallback path; test verifies the prefix reaches the spawned `omp --print` argv.
- **gateway-design-v1.md v1.1**: Doc previously claimed cron is "独立 spawn omp --print" and "不经过 AgentBridge" — both stale since cron agent tasks now reuse the warm bridge via `AgentBridge.executePrompt()`. Rewrote §2.4 one-liner, §3 ASCII diagram + cron row, §3.1 cron row, §4.1 component mapping (cron leaf = `bridge.executePrompt` / fallback), §4.2 spawn relationships (warm path doesn't spawn), §7.3 session naming convention (`cron_<id>.jsonl` prefix), new §7.4 warm-bridge reuse flow with the full 6-step sequence + session-restore + inactivity + delivery-retry diagrams, §8.2 cron flow, §9.2 filesystem layout (added `~/.omp/gateway-data/scheduler/{tasks,logs,logs/delivery-failures.jsonl}`), §10.1 added `executePrompt`/`forwardWithMeta`/`setModel`/`getSnapshot`/`abort` to AgentBridge row, §11.1 added 5 cron-specific failure rows (no-accountId, warm-fail→fallback, skills/preScript warning, inactivity watchdog, delivery failure), §13 future moved "知识库自动同步" to 已实施 (cron 实现) and added "cron 路径硬工具限制" + "cron 路径独立 persona" as future work. gateway-implementation-v1.md bumped to v2.1 to match.
- **Cron list shows DELIVERY column**: `pi-gateway cron list` now renders a `DELIVERY` column showing the count of recent (last 24h) delivery failures for each task. `✓` means no recent failures; `× N` shows the count. Backed by `getRecentDeliveryFailureCount(taskId)` which reads the global `delivery-failures.jsonl` log (cached by mtime, so per-row reads are O(1)). Operators see at a glance which task results never made it to the configured channel without grepping the JSONL. New `formatDeliveryFailureCount` helper in `src/scheduler/types.ts`; 5 tests cover the empty / recent / windowed / per-task / row-inclusion cases. The existing column-layout test was rewritten to match the new 10-column layout (NAME TYPE AGENT STATUS CRON MODEL CHANNEL LAST DELIVERY NEXT RUN, 148-char header).

- **Cron scheduler fields**: Added `model`, `provider`, `enabledToolsets` to `ScheduledTask` and `TaskFileDefinition` for per-task LLM model/provider overrides and toolset restriction. Removed redundant `noAgent` (shell == noAgent). SQLite migration adds columns idempotently. CLI flags `--model`, `--provider`, `--toolsets` on `cron create`. JSON5 task files also support the new fields.
- **Injection scan for agent tasks**: Agent task prompts are scanned at execution time for prompt injection patterns (ignore instructions, read secrets, rm -rf). Blocked prompts fail with exit 1 and a clear error message.
- **Cron reuse of existing AgentBridge**: Cron agent tasks with an `accountId` now reuse the already-warm `omp --mode rpc` process via `bridge.executePrompt()` instead of spawning a new `omp --print` subprocess. If the task specifies a different `model`/`provider`, the bridge's model is switched before execution and restored afterward. Falls back to `omp --print` if no matching bridge is found.
- **Auto-fill deliver/deliverUser on task creation**: CLI `--source-channel` and `--source-user` flags let the caller auto-populate `deliver`/`deliverUser`. `from-message.ts` also forwards sourceChannel/sourceUser.
- **Gateway status shows bridge details**: `omp gateway status` now renders per-account bridge state (`idle`/`busy`/`error`), PID, crash count, pending prompt count, and circuit breaker status inline. No `--json` required.

- **DingTalk reply chrome (v1 of OpenClaw-style visualization)**: New `formatDingTalkReply` formatter composes the agent's reply into a single markdown message with four visual sections — `quoteContent` (the inbound message as a `> 💬 **Sender**: body` blockquote so group chats retain context), an optional `**工具**: read × 3, edit × 1` tool-summary line listing the tools invoked (with call counts and error tail), the cleaned main answer, and a footer status line `model · effort · taskTime · tokens · dapiCalls · agent`. The formatter is a pure function in `packages/pi-gateway/src/channels/dingtalk-formatter.ts`; it's the v1 land before the OpenClaw AI Card (PROCESSING → INPUTING → FINISHED) ships in v2. Long answers are truncated to the DingTalk 4000-char cap with the chrome (header + footer) preserved. For `meta.isFallback` (circuit open, recovery, "agent 未返回内容") the chrome is stripped — fallback strings are user-facing errors and should not be padded with status-line noise. 29 unit tests cover each section (quoteContent for text/markdown/image/file/voice/video, tool summary collapse + count + error tail, status line for all 6 fields plus missing-everywhere, sanitization, truncation, section ordering).

- **AgentBridge metadata exposure**: New `forwardWithMeta` method on `AgentBridge` returns the full `AgentResponseMeta` (model, provider, usage breakdown, agent duration, gateway task duration, tool calls with arguments, tool results with error flags, aborted/fallback flags) so callers can render richer replies than a single text blob. The original `forward` is preserved as a thin wrapper that returns just `meta.text` — existing call sites and tests are unaffected. The meta is built by mining the RPC event stream: the last `message_end` with `role: "assistant"` contributes model/provider/usage/duration, every assistant `message_end`'s `content[]` array contributes the `ToolCall` items, and every `message_end` with `role: "toolResult"` contributes the result list. Field extraction uses real `@oh-my-pi/pi-ai` types (`AssistantMessage`, `ToolResultMessage`, `ToolCall`, `Usage`) with the bridge's deliberately narrow inline `AgentEvent` cast at the wire boundary. A 3-case end-to-end test (`test/dingtalk-reply-e2e.test.ts`) pins the contract: a rich fake RPC emits a full `AssistantMessage` (model/provider/usage/duration + a `read` tool call) and the test asserts every field round-trips into the rendered reply markdown.

- **`Channel.formatReply` interface**: New optional `formatReply(meta, inbound, context)` method on the `Channel` interface lets each platform opt into richer reply rendering. The gateway calls it after every agent run via the channel registry; channels that don't implement it (e.g. future Feishu / WeChat additions) get a plain-text fallback. DingTalk's implementation composes a markdown `OutboundMessage` from the formatter output and stamps the inbound `sessionWebhook` + `accountId` so the existing `sendMessage` path posts it unchanged. New `ReplyFormatterContext` type carries `accountId`, `agentName` (v1 falls back to `accountId`; a v1.1 follow-up can read `<agentDir>/mission.md` for a real name), and `dapiCalls` (v1 hardcoded to 0; a follow-up can wire channel-side counting).

- **`SessionManager.enqueueWithMeta`**: New method mirrors `enqueue` but returns the full `AgentResponseMeta` instead of just the formatted text. Used by the gateway's `#handleInboundMessage` for the formatReply path. The legacy `enqueue` (returning text) is unchanged so the cron scheduler and CLI /model commands that still want just the text keep working. The queue-full guard now returns `null` on this path (vs the legacy `enqueue` returning the localized `QUEUE_FULL_MESSAGE`) — the caller is expected to handle the empty case explicitly.

- **Multi-account CLI interactive mode**: `sendDirectMessage` now accepts an optional `accountId` parameter. In multi-account mode, the CLI shows available accounts and supports `@<accountId> <message>` prefix to route messages to a specific per-account bridge, `/switch <accountId>` to change the default, and auto-selects the first account when no prefix is given. Single-account mode remains unchanged. New `#resolveDirectBridge` method on Gateway selects the correct `AgentBridge` based on accountId: specified account → that account's bridge; no accountId + single-account mode → default bridge; no accountId + multi-account mode → returns null with a help message listing available accounts. The CLI prompt changes from `>` to `[<accountId>] >` in multi-account mode.

- **DingTalk end-to-end test**: New test (`test/dingtalk-gateway-end-to-end.test.ts`) exercises the real `DingTalkChannel` (parsing, dedup, allowlist, outbound `sendMessage`) wired into a real `ChannelRegistry` + `SessionManager` + `AgentBridge` + `SQLiteSessionStore` pipeline. The DingTalk Stream SDK is replaced by a tiny `EventEmitter`-based fake `DWClient` injected via a `protected createDWClient()` factory seam, so the test can drive the real `#handleMessage` callback path without opening a WebSocket. Outbound `sessionWebhook` POSTs land in a local `Bun.serve` capture server. 4 cases: DM text round-trips through channel → bridge → channel, duplicate business `msgId` is dropped at the channel layer, group @mention reaches the bridge, and DM from a user outside the allowlist is blocked (only the channel's built-in denial message is sent; no agent call).
- **`DingTalkChannel.createDWClient` test seam**: New `protected` factory method on `DingTalkChannel` that returns the `DWClient` instance. Default implementation constructs the real SDK client with the production configuration (autoReconnect off, no debug). Tests subclass and override to inject a fake SDK client that captures the robot-callback registration. No runtime behaviour change.
- **Full DingTalk inbound message-type coverage**: `parseRobotMessage` now handles every `msgtype` the DingTalk robot API can deliver, in addition to the existing `text` / `markdown` / `picture` / `audio` / `file` support. New branches: `video` (parsed into `MessageContent.video` with `url` / `filename` / `duration` / `videoType`; the downloadCode resolves to a local file path via the media downloader), `richText` (split into an ordered array of `InboundMessage`s — text segments become `text` items, `picture` items become `image` items — so the downstream agent reconstructs the original layout). The parser signature changed from `(raw, channelId, accountId, messageId?) => InboundMessage | null` to `(raw, channelId, accountId, messageId?, downloader?) => Promise<InboundMessage[]>`: the array return type accommodates the richText split, the optional 5th `MediaDownloader` argument injects the same `downloadMedia` from `dingtalk-media.ts` that the rest of the channel already uses. The `DingTalkChannel` exposes a matching `protected createMediaDownloader()` factory seam (default wraps the production downloader, tests can override). `agent-bridge#extractText` was extended to render `image` / `file` / `voice` (without ASR text) / `video` as `[image (<name>): <path>]` / `[file: <name> -> <path>]` / `[voice: <path>]` / `[video: <name> (<type>, <ms>ms) -> <path>]` so the agent always sees a concrete reference it can `read`. 8 new unit tests cover all branches: text / markdown / picture / audio / video / file / richText-splitting / downloader-resolution / downloader-failure-fallback. 1 new end-to-end test pins a 4-block richText payload (text + image + text + image) and asserts (1) ordered delivery to the bridge, (2) the rendered agent prompt contains real local file paths (not `downloadCode:...` placeholders).

- **`cron list` shows an `ACCOUNT` column**: Each task row now renders the channel account that owns the agent context for the task (e.g. `hr`, `opencode`, `ops/hr`, or `—` when unset). Bound at task creation time via `cron create --account <accountId>` and resolved at runtime to the account's `agentDir` from `gateway.json` (`channels.dingtalk.accounts[<id>].agentDir`). The agentDir is then used as the `Bun.spawn` cwd so `omp` finds the correct `.omp/config.yml` for the task's owning account. If the account is later removed from `gateway.json`, the task falls back to the gateway cwd with a warning (no break). Storage: new `account_id` column on `tasks` with an idempotent `ALTER TABLE` migration; existing tasks display `—` and continue to run as before. **Header label was renamed from `ACCOUNT` to `AGENT`** to match the original "AGENT column" spec; the underlying field and storage column are still `accountId` / `account_id` (channel account key, not path) because accountId is the user-facing identity and agentDir is a path on disk that can change. The lookup contract is now exported as `resolveAgentCwd(accountId, config)` for unit testing, with 9 regression tests pinning the behaviour for known / unknown / missing-channel / empty-string / cross-channel cases.
- **`cron update <name>`**: New subcommand to mutate task fields in place, so existing tasks can be rebound to a different channel account (or have their delivery target / timeout changed) without delete+recreate. Supported flags: `--account <id>` / `--clear-account`, `--deliver <channel>` / `--clear-deliver`, `--deliver-user <id>` / `--clear-deliver-user`, `--timeout-ms <ms>`. A `--<field>` paired with its `--clear-<field>` on the same invocation is rejected with exit 1. The dispatch and help text are wired through `cli.ts`; the function is re-exported from the scheduler package.
- **`cron reconcile [--apply]`**: One-shot CLI for backfilling `accountId` on legacy tasks that pre-date the AGENT column. Dry run by default (prints a NAME / TYPE / SUGGEST / REASON table and tells the user to re-run with `--apply`); `--apply` actually writes the bindings. Heuristic, in priority order: (1) task name starts with `<accountId>:`, or (2) task name starts with `<agentDir basename>:`. The colon-delimited prefix rule is deliberate — a naive substring match would falsely bind `hr3-daily` to the `hr` account. The match logic is exported as `suggestAccountBinding(name, accounts)` and unit-tested with 9 cases including slash-keys, missing agentDir, empty-string agentDir, and the accountId-wins-over-basename priority. The reconciler never touches already-bound tasks.
- **Inbound cron task creation from channel messages**: Closes the user-facing gap between DingTalk (or any channel) messages and the scheduler. A message that starts with `/cron create <schedule> -- <command...>` now creates a task in the owning account's `<agentDir>/cron/tasks/<name>.json5` (matching the skeleton's directory layout) and also inserts it into the global scheduler DB so the engine picks it up on its next tick. The `--` separator is deliberate — cron expressions themselves contain spaces, so splitting on whitespace would corrupt `0 8 * * *` into `schedule="0", command="8 * * *"`. The full flow lives in `gateway.ts#handleInboundMessage` and is extracted into `createCronTaskFromMessage` in `src/scheduler/from-message.ts` for unit testing. The DB insert is atomic with the file write: a DB failure rolls back the file so no orphan definitions are left behind. Non-cron messages fall through to the normal LLM agent path unchanged. 13 new smoke tests pin the parser, the per-agentDir path, the DB roll-back on failure, and the error contracts (not-cron-intent / no-account-id / no-agent-dir / db-failed).
- **Outbound delivery smoke test**: New end-to-end test (`test/scheduler-outbound-delivery-smoke.test.ts`) that exercises the cron task → DingTalk delivery path with mocked fetch. Creates a real task in a temp DB, calls `cronRun`, captures both the OAuth `accessToken` and `batchSend oToMessages` HTTP calls, and asserts that (1) the right account's `appKey` is sent, (2) the access token lands in the `x-acs-dingtalk-access-token` header, (3) the message body contains the task output, (4) `deliver` (not `accountId`) is what picks the sending account, and (5) tasks with no `deliver` do not touch DingTalk at all.
- **`cron list` shows a `CHANNEL` column**: Each task row now renders the `deliver` target (e.g. `dingtalk:hr`, `dingtalk:user:601590212`, or `—` when unset) so users can see at a glance which channel a scheduled task's results will land in. The `deliverUser` field is intentionally not inlined into this cell (it's an orthogonal proactive-send destination); use `cron list --json` to see the full record. Over-long task names are truncated to 18 chars with an ellipsis (`omp-atomix:wiki-c…`) so they can't overflow into the `TYPE` column.

### Changed

- **Hierarchical execution-log layout**: Scheduler execution logs are now written to `<gateway-data>/scheduler/logs/by-task/<slug>/<YYYY-MM-DD>.jsonl` instead of `<gateway-data>/scheduler/logs/<sanitized-name>.jsonl`. The directory slug is `slugify(taskName)` — kebab-case, pinyin for CJK, capped at 32 chars. All runs of a task on the same day go in one file. One file per day keeps the append-only semantics intact and makes day-by-day cleanup trivial. Backward compatibility: readers (`readExecutionLog`, `pruneExecutionLog`, `pruneAllLogs`) also walk the legacy flat files at the logs root. New `setLogRoot()` / `getLogRoot()` helpers make the log root injectable for tests.
- **Slug cache on first write**: Each task computes its directory slug once (sync, via `pinyin-pro`) and caches it for subsequent writes. The first write for a CJK-named task already lands in the pinyin directory (no async/sync split).
- **Fixed CJK task name handling**: The previous `replace(/[^a-zA-Z0-9_.-]/g, "_")` sanitizer turned `omp-atomix:wiki-changelog:01-算法模块` into `omp-atomix_wiki-changelog-agent_01-____.jsonl` (Chinese characters erased to underscores). The new path resolves the same task to `logs/by-task/omp-atomix-wiki-changelog-01-suan-fa-mo-kuai/`.
- **`pi-gateway install` now seeds agentDir through `omp agent init`**: The interactive DingTalk install wizard (`pi-gateway install`) now delegates agent directory creation to the public `runAgentInit` handler exported from `@oh-my-pi/pi-coding-agent/cli/agent-cli`, so install and the `omp agent` CLI share one source of truth for the skeleton layout. The wizard also adds an optional "Mission 文件" prompt so users can seed a custom `mission.md` at install time without leaving the flow.

### Fixed

- `pi-gateway install` output: the "下一步" hint now lists `omp agent show <accountId>` and `omp agent validate --dir <agentDir>` so users can verify the agentDir created during install. Also fixes a missing path separator in the "编辑 `<agentDir>/.omp/config.yml`" hint that previously rendered as `agentDir.omp/config.yml`.
